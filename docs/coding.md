# coding.md — AI Coding Agents 的 Spec-Driven 开发守则

> 本文档是所有项目中 AI Coding Agents 的最高层级工作约定。任何加入项目的 Agent 必须先读本文件，再读项目的**长存文档**（§2.1），然后才开始动手。请把本文件加上项目的长存文档，当作你一切工作的权威上下文。
>
> 本守则取代旧版"文档驱动开发"守则。它保留了被实践证明有效的部分（升级纪律、原则宪法、决策记忆、code-as-docs），并修正了无效的部分（文档过多且彼此强耦合、僵硬的"先文档后代码"瀑布流、叶子层 spec 详尽到与 Agent 自身判断相抵触、以及旧文档悄悄束缚后续工作）。

---

## 0. 核心理念

我们实践 **spec-driven development（SDD）**：用结构化的 spec 在实现之前与实现周围承载意图与契约，并作为人类与 Agent 共享的事实来源。但我们采用 SDD 时带了五条从实践中学到的修正。这五条是整份文档的脊梁，其余都是机制。

### 0.1 SDD 是一个回路，不是瀑布

朴素形态的 SDD——"先写完整 spec，再实现，然后冻结 spec"——会失败，因为大多数真实约束与取舍在**写 spec 时是看不见的**，只在实现和测试中暴露。若把每一次这样的发现都强行塞进"文档错了、我必须停下来上报"的重型闸门，会烧掉大量精力，并制造一种虚假的掌控感。

所以 spec 与代码的关系是一个**回路**：

```
   意图 ──► spec（契约） ──► 实现 + 验证 ──► 发现
    ▲                                          │
    └────────────── 回流修订 spec ◄────────────┘
```

实现被允许、也被期望把发现回流到 spec。纪律在于一个发现**允许落在哪里**、以及**如何落**（见 §4 与 §5），而不在于是否允许发生发现。

### 0.2 两个文档家族：长存 vs 时间线

当一种生命周期被强加到两类截然不同的内容上时，文档就会失效。我们把每个项目的文档劈成两个**生命周期相反**的家族：

- **长存层（memory bank）。** `philosophy`、`requirements`、`design`、`blueprint`、`goal`。它们表达持续的意图与护栏。它们**少而精，并在项目生命周期内就地更新**。Agent 读这一层是为了*理解意图*，而不是照着脚本执行。
- **时间线层（开发日志）。** 每一个开发任务——交付一个功能、修一个 bug、做一次重构——产出一个**episode**：一份 `spec`（该任务的契约）加一份 `plan` 加一份简短的 `notes`。完成后该 episode **按时间戳归档、永不删除**。归档的受众是**人类**，不是 Agent：它保存"来时的路"——当时遇到了什么问题、做了什么考量、所以这个模块为何变成现在这样。

最重要的一个推论：**归档的时间线 episode 默认不进入 Agent 的活动上下文。** 它们是给人类考古、以及给有意查阅用的冷存储，而不是常驻指令。这正是防止旧的、措辞强烈的任务文档悄悄束缚或搞混后续工作的机制。陈旧的 spec 若在完成时已被请出工作集，就无法再腐蚀它。

> 放置文档的经验法则：*当前任务交付之后，这条内容是否仍然为真、仍然有用？* 若是，它属于长存层、就地编辑。若它只描述"我们现在正在做什么"，它就是一个时间线 episode，任务完成时归档。

### 0.3 契约精确，构造自由

这是"文档该精确到什么程度"以及"Agent 有多大自由度"的可操作标准：

> **锚定契约（边界）。刻意放空构造（内部）。**

|            | 契约 / 边界                                                  | 构造 / 内部                              |
| ---------- | ------------------------------------------------------------ | ---------------------------------------- |
| 覆盖内容   | 签名、类型、错误行为、不变量、**业务意图（为什么 / 为谁）**   | 函数体、内部拆分、局部算法、命名         |
| 所需精度   | **详尽且无歧义**                                             | **刻意不写满**                           |
| Agent 自由度 | **低**——契约具有约束力                                       | **高**——只要契约成立，随便发挥           |

我们**不**在文档里预先写函数体，也**不**再追求旧版那个"连很小的模型都能照 spec 填出函数体"的目标。那个目标把精度错配到了内部，而内部恰恰是一个有能力的自主 Agent 应当主导之处——它正是"小任务被大锤砸核桃"的直接成因。精度集中在出错代价高、且跨模块的地方：契约层与 *why*。完整规则见 §4，包括它如何重塑升级触发条件。

### 0.4 文档重量随任务规模缩放

一套工作流无法同时适配一行 bug 修复和一个新子系统。把重型多文件 spec 仪式套到一个小改动上，是最常见的 SDD 反模式（见 §6）。Agent 产出的文档量**随任务的规模与不可逆性缩放**，按 §6 的分级执行。拿不准时，少做仪式，多依赖已经存在的长存层。

### 0.5 用户拥有最终决策权

这里所有规则都从属于用户的明确决定。当用户指令与本文件或既有长存文档冲突时，以用户为准——但 Agent 必须**先把冲突摆出来**（§1.1）再行动，让用户是在信息充分的前提下决策，而不是无意中决策。

## 1. 顶层原则

三条原则贯穿每一个任务，不得被悄悄违反。

### 1.1 主动升级（有校准，而非条件反射）

旧版守则让 Agent 几乎遇到任何意外都升级。在更自主的 Agent 身上，这会造成持续打断，并把 Agent 训练成"把问题甩回给用户"。校准后的规则：

**仅当一个决策属于以下一种或多种时才升级：**

- **改变契约**——会改动 `spec` 中声明的对外可见接口、类型、错误行为或不变量（见 §4.2）。
- **违反原则**——会与某条 `philosophy` 条款、某条 `blueprint` 约束、或长存层中已声明的否决相抵触。
- **跨模块**——会改动另一个模块的源代码、spec 或行为。
- **不可逆 / 爆炸半径大**——数据丢失、迁移、安全态势、公开 API，任何撤销代价高昂的事。
- **真正的文档冲突**——长存文档互相矛盾，或某个 spec 在工程上不可行。
- **用户自相矛盾**——用户的最新指令与早先的指令、或与既有长存文档冲突（人会遗忘、会改主意；不要假设用户自洽）。

**不要升级**那些纯属内部、局部、可逆的决策——这些 Agent 自己拍板并继续推进（必要时在 episode 的 `notes` 里记一笔）。这个区分正是 §0.3 的全部意义所在。

**如何升级**——绝不把一个生问题原样甩出去、让用户从零开始想：

1. 精确陈述问题：在哪、是什么。
2. 给出你自己的分析与一个具体建议，并以长存文档为依据。
3. 请用户确认你的建议，或另选一条路。

> 示例："`auth/spec` 写 `verifyToken()` 返回 `User`，但 session 模块调用时按 `User | null` 处理。依据 `philosophy` 中'显式胜于隐式'一条，我建议把契约改为 `User | null` 并更新两处调用点。照此进行，还是另作处理？"

升级之后：用户决策 → **先更新契约/长存文档** → 代码再跟进。一个值得升级的决策，也值得在 episode 的 `notes` 里记一行；若它是跨切面的，则记入模块的决策记忆（§3.8）。

### 1.2 反厂商锁定

技术选型必须保持可移植、可替换。避免紧耦合、难以退出的依赖（例如绑死单一云的专有数据库，或掌控你认证模型的专有身份服务）。任何有锁定倾向的依赖，必须在 `design` 中记录其接受/否决的理由（若预期未来要迁移，则在 `blueprint` 中记录）。

### 1.3 隐私优先

若项目涉及隐私敏感（云存储、笔记、健康数据等），用户会明确声明并提供 `docs/privacy.md`。该文件存在时，在任何技术决策前先读它，并把其约束视为高于普通工程偏好。该文件不存在时，不要自行臆造隐私需求。

## 2. 两个文档家族

### 2.1 长存层（memory bank）

在项目（或模块）生命周期内就地编辑，保持少而精。

| 文件              | 回答                                                                  | 备注 |
| ----------------- | --------------------------------------------------------------------- | ---- |
| `philosophy.md`   | 我们持有哪些原则、为什么？我们在原则上否决了什么？                     | "宪法"。见 §3.1。 |
| `requirements.md` | **业务 / 产品**意图是什么——我们在为谁、构建什么、为何重要？           | 旧版守则缺失的业务根基。见 §3.2。 |
| `design.md`       | 架构**当前**长什么样——形态、组件、数据流、边界？                      | 当前的结构事实。见 §3.3。 |
| `blueprint.md`    | 我们刻意**暂不**构建、但绝不能把自己锁死在外的东西是什么？            | 面向未来的反锁定。见 §3.4。 |
| `goal.md`         | 我们持续朝之掌舵的**北极星目标**是什么？                              | 长存的目标。见 §3.5。 |

并非每个项目或模块都需要全部五个。小项目可能只有 `requirements` + `design`。`philosophy`、`blueprint`、`goal` 在确有内容时才出现。

### 2.2 时间线层（开发日志）

每个开发任务是一个 **episode**。活动中的 episode 以工作集形式存在于模块根；完成的 episode 被移入 `timeline/`，以完全限定的带时间戳名称归档，且从此不再编辑。

一个 episode 包含：

- `spec.md`——**本任务的契约**：接口、类型、错误、不变量，以及本任务自己的目标/DoD。这是精确且具约束力的一层（§0.3、§4）。它**引用**自己推进的是哪条 `goal`，而不重述它。
- `plan.md`——本任务**如何**执行：实现路径、关键技术选择、坑点。它的第二个职责是**省上下文**——后来的 Agent 读 plan，而不必从整套 `design` 里重新推导方案。
- `notes.md`——一段简短的日志，记录实际发生了什么：遇到的问题、权衡的考量、做了什么决定及其原因。这是给未来人类读者的"来时的路"。

归档 episode 命名：

```
timeline/<YYYYMMDDHHMM>.<kind>.<topic>/
    spec.md
    plan.md
    notes.md
```

`<kind>` ∈ `feature | bugfix | refactor | migration | experiment | hotfix`（用户可增补类别）。`<topic>` 是简短的 snake_case 标签。例：`timeline/202606031200.feature.token_revocation/`。

> **受众纪律。** `timeline/` 归档是为*人类*回顾历史而写。Agent **默认不**把归档 episode 载入上下文。只有在明确需要时才查阅（"这里为什么选了 rotation？"），即便查阅，也把它当作*历史叙述*，绝不当作常驻指令。这就是把陈旧任务文档请出工作集的机制（§0.2）。

### 2.3 运维文档（轻量、按需）

- `changelog.md`——带**冒泡**的变更记录（§3.9）。推荐。
- `manifest.md`——把文档映射到实际代码文件的清单。**可选**；在大模块上、当审阅者想快速做文档↔代码交叉核对时有用。小模块直接读代码树即可。
- `runbook.md` / `manual.md`——运维指南 / 终端用户手册。仅当模块有运维关切、或交付面向用户的产物时才有。

### 2.4 递归与继承（"分形"规则）

大项目有模块，而**每个模块都可以携带自己的、限定于其业务范围的长存层**（`auth/` 可以有自己的 `philosophy`、`requirements`、`design`、`blueprint`、`goal`）以及自己的 `timeline/`。为避免冗余翻倍、避免重新引入"旧措辞反噬"的问题，子级长存文档遵守三条规则：

1. **继承。** 子级长存文档继承父级；父级的原则与意图除非被显式特化，否则一律适用。
2. **只写增量 + 引用，不重述。** 子级只记录对它*本地*的东西——自己的原则、自己的业务边界、自己的架构——并**援引**父级条款而非复制。（`auth/philosophy.md`："继承根 `philosophy.md`。本地新增：token 对客户端不透明——见根条款'显式胜于隐式'。"）
3. **可特化，不得静默抵触。** 子级可以*收窄或扩展*父级原则。子级**不得**悄悄违背它。子级需求与父级原则之间的真实冲突，是一次升级（§1.1），由用户裁决，而非糊弄过去。

跨模块决策记录在**受影响最大**的模块的时间线/决策记忆中，邻居模块以一行交叉引用指向它。

### 2.5 物理布局（示例）

```
project_root/
├── README.md                  # 普通开源 README（人类门面）
├── AGENTS.md                  # 简短介绍 + 强力跳转到 docs/
│
├── docs/
│   ├── coding.md              # 本文件（逐字副本；项目内不修改）
│   ├── README.md              # 文档索引 + 模块地图
│   ├── philosophy.md          # 根长存层
│   ├── requirements.md
│   ├── design.md
│   ├── blueprint.md           # 可选
│   ├── goal.md                # 可选
│   ├── privacy.md             # 可选，仅隐私敏感项目
│   │
│   ├── auth/                  # 一个模块：自己的长存层 + 时间线
│   │   ├── requirements.md    #   （增量 + 对根的引用）
│   │   ├── design.md
│   │   ├── philosophy.md      #   可选，仅当它有本地原则时
│   │   ├── spec.md            #   ← 活动 episode 的契约
│   │   ├── plan.md            #   ← 活动 episode 的 plan
│   │   ├── notes.md           #   ← 活动 episode 的日志
│   │   ├── changelog.md
│   │   ├── decisions.md       #   可选 ADR 式跨 episode 记忆（§3.8）
│   │   └── timeline/          #   归档 episode（永不删除）
│   │       ├── 202604180900.feature.login/
│   │       └── 202605102350.refactor.session_store/
│   │
│   └── api/
│       └── ...
│
└── src/                       # 实际代码
    └── ...
```

`docs/` 树反映的是**逻辑**模块分解；它不必与 `src/` 一一对应，但在实际可行处应对齐。`timeline/` 在第一次归档 episode 时才创建，不预先建立。

## 3. 逐文件说明

### 3.1 `philosophy.md` — 宪法

一份扁平的原则清单，每条都陈述、论证、举例、并划定边界：

```markdown
## <原则名>

**陈述：** <一两句话。>
**为什么：** <推理，源自与用户的真实讨论。>
**适用如：** <本项目里一两个具体例子。>
**何时让位：** <该原则让位于另一原则的边界情形。>
```

原则应当稳定、跨全项目、彼此正交；若两条经常冲突，记录默认谁胜。**Agent 不得自行修改 `philosophy.md`。** Agent 可以在初始搭建时通过忠实转录用户表述来起草它，可以自由援引它，也可以通过升级*提议*修改——但"想悄悄重写一条原则"这股冲动，意味着 Agent 与用户已经分歧，而这恰是该升级的时刻（§1.1）。

### 3.2 `requirements.md` — 业务 / 产品意图

旧版守则缺失的根基。在讨论*怎么*构建之前，Agent 需要理解*用户的真实业务是什么*、以及*为何这对他们重要*。用产品语言写，而非技术语言：

- 我们在为谁、解决什么问题？
- 什么样的结果定义成功（用用户/业务术语）？
- 范围边界——什么在内，什么明确在外。
- 已知约束（合规、性能、容量、截止日期）——它们塑造后续每一个决策。

行为导向的表述（用户故事、场景）受欢迎但非强制。要对*真实*的问题规模诚实——别把一个小改动膨胀成一堆臆造故事的仪式（§6）。

### 3.3 `design.md` — 当前架构（形态，而非契约）

模块**当前**长什么样：组件分解、数据流、状态住在哪里、谁可以变更它、对外边界与协议、本模块负责的横切关切（日志、事务、重试、缓存）。散文加可选的 ASCII/Mermaid 图。它也记录**考虑过并否决的结构性备选**，让这个形态被理解为一个选择，而非偶然。

`design.md` 回答"它是怎么搭起来的"，而 `spec` 回答"具约束力的契约是什么"。经验法则：如果删掉 `design.md` 只留活动 `spec`，Agent 还知道如何把模块拆成文件和组件吗？若它得靠猜架构，那么 `design.md` 正在发挥作用。

顶层与中层模块必需；单一职责的叶子模块往往不需要。

### 3.4 `blueprint.md` — 刻意的未来、刻意的不做

记录我们**现在不**构建、但预期以后会构建的东西，以及——它真正的目的——**这对当前设计施加的约束，使我们不至于把自己锁死在外。** 它是"局部最优、却让项目日后搁浅"那类架构的解药。

```markdown
## <未来能力>

**做什么 / 大致何时：** <我们预期会加什么，以及大致时间窗。>
**为何推迟：** <现在没有足够的时间 / 资源 / 清晰度。>
**对当前设计的约束：** <今天的架构必须为之保留什么开口，使它日后无需重写即可落地——例如"保持存储接口与后端无关；不要假设单区域数据库。">
**若忽视，预估债务：** <若把自己锁死，日后回补的代价。>
```

做架构的 Agent 必须读 `blueprint.md`，并把当前选择与这些未来约束权衡——这是反锁定（§1.2）的一个具体实例。

### 3.5 `goal.md` — 北极星

项目（或模块）持续朝之掌舵的目标，层级高于任何单个任务。它是长存的，随方向变化就地更新。每个时间线 episode 引用它推进的是目标的*哪一部分*；episode 级的目标本身住在那个 episode 的 `spec` 里，不在这里。`goal.md` 要短——它是罗盘，不是 backlog。

### 3.6 `spec.md` — 契约（精确、具约束力的一层）

**当前任务/episode**的契约。这里精度是强制的（§0.3、§4）。它是实现方与验证方都必须能依赖、且无需读对方工作的共享事实来源。

每一个对外暴露的单元，都必须以**机器可读**形式（签名/类型/schema 用代码块；错误码用表格）**和****人类可读**形式（一段 doc-comment 块——Doxygen/JSDoc/Rustdoc 风格——加一段意图散文）给出：

- **签名**——名称、参数、参数类型、返回类型。
- **行为契约**——给定这些输入，产生什么输出与副作用。
- **错误契约**——在什么条件下产生哪些错误、它们意味着什么。
- **不变量 / 前后置条件**（适用时）。
- **类型确切性**——例如结果是整数 `1` 还是字符串 `"1"`？这必须无歧义，且对于不寻常选择的*意图*必须写明（例如"金额以字符串编码十进制，因为我们需要超出 IEEE-754 的精度"）。在此写明意图，正是日后让验证方能把真契约与 bug 区分开的依据——见 §5。

spec 还要陈述**任务级目标 / DoD**：本任务何谓完成、什么被推迟、什么明确在范围外。

spec **不是**规定函数体、内部辅助函数或局部算法选择的地方——那些是构造（§0.3），属于实现方的判断。

### 3.7 `plan.md` — 如何，且省上下文

当前任务的实现计划：可执行粒度的路径与步骤、关键技术决策、以及**坑点**（陷阱、性能陷阱、边界情形）。它的第二个目的是经济性：后来的 Agent 读 `plan.md` 来恢复既定方案，**而不必重新载入整套 `design`**，从而省下上下文预算。

plan 不需要详尽到函数体——那会过度规定内部（§0.3）。它只需详尽到工作能在中途接续、无需重新推导方案即可。

### 3.8 时间线与决策记忆

任务完成时，把 `spec` / `plan` / `notes` 三件套移入 `timeline/<时间戳>.<kind>.<topic>/` 并冻结（§2.2）。`notes.md` 的开头几行应记录结果：completed | abandoned | superseded，外加 1–3 行小结。

对于**跨 episode** 的决策——那些寿命超过任何单个任务的架构选择（"我们选 PostgreSQL 而非 MySQL，因为……"）——模块根下一份可选的 append-only `decisions.md`（ADR 风格）充当长存的决策记忆。条目只追加：日后的推翻得到一条**新**条目并交叉引用旧条目，绝不编辑旧条目。这是防止 Agent（或未来的人类）重新提出一个早已被考虑并否决的想法的最便宜的保险。

> 区分：episode 的 `notes` ="本任务里发生了什么"。`decisions.md` ="一个约束所有未来任务的选择"。`changelog.md` ="改了什么"。三者之间不要重复，互相引用即可。

### 3.9 `changelog.md` — 带冒泡的变更记录

在每个完成的任务结束时更新。冒泡语义：仅限模块内部的变更只更新该模块自己的 changelog；触及模块**对外接口或行为**的变更，更新该模块的 changelog（完整细节）**并**在**父**模块的 changelog 中加一行小结 + 指针，逐级冒泡。父级 changelog 是"小结加索引"，不是细节的副本。

### 3.10 `manifest.md`（可选）与 3.11 `runbook.md` / `manual.md`（可选）

`manifest.md`：已实现内容与文件/目录布局的清单，在提交时与代码保持对齐，用于那些"文档↔代码交叉核对"有价值的大模块。`runbook.md`：如何运维该模块（运行、迁移、消费其接口），给运维与上游开发者。`manual.md`：当模块交付面向用户的产物时的终端用户文档。只用模块确实需要的那些。

## 4. 精度标准（契约 vs 构造）

本节把 §0.3 落到可操作，并回答"文档该精确到什么程度、Agent 有多大自由度"。

### 4.1 锚定什么、放空什么

- **精确锚定（低自由度）：** 一切对外可见或跨切面的东西——签名、类型、错误行为、不变量——以及它们背后的**业务意图**。这里禁止歧义，因为这恰恰是让验证不可能的东西（契约模糊时，验证方无法分辨 bug 与特性）。
- **放空（高自由度）：** 一切内部的东西——函数体怎么写、模块内部怎么拆、用哪个局部算法或数据结构、怎么命名。只要契约成立，这些归 Agent 自己掌管。

### 4.2 被重塑的升级触发条件

这是化解那场让旧瀑布如此昂贵的"升级风暴"的关键：

- 一个落在**构造**层的发现 → **拍板并推进。** Agent 运用判断、实现、并（若值得）在 `notes` 里记一行。不升级。
- 一个会改变**契约**层、违反原则、跨越模块边界、或不可逆的发现 → **reconcile 和/或升级**（§1.1）。先更新 spec/长存文档，再改代码。

因为大多数实现期惊喜都是内部的，所以大多数被自主消化，文档也就永远无需下沉到函数体精度。

### 4.3 爆炸半径启发式

拿不准一个决策属于哪一层时，问它的爆炸半径有多远：决策越**不可逆**或越**跨模块**，就越属于精确锚定的契约层、也越值得升级；越**局部且可逆**，就越是 Agent 直接掌管的自由构造。

## 5. 验证与交叉校验

AI coding agent 有一个典型失败模式：**对着错误的答案改问题。** 测试红了，Agent 体感的目标是"让它变绿"，于是沿阻力最小的路径放松断言或契约。但反过来——一旦现实与 spec 有出入就教条地报错——同样是错的，因为现实可能是*对的*，而 spec 只是没说或过时了（后端故意返回字符串 `"1"`，因为金额为精度起见以字符串编码十进制）。下面的纪律在两者之间穿线。

### 5.1 契约及其意图是唯一权威

验证方的事实来源是**契约（`spec`）加意图（`requirements` 以及 spec 里的"为什么"）**——**绝不是**它正在检查的那个产物的当前状态。这就是我们所说的"隔离"：不是一道物理墙，而是一道**认识论**的墙。

### 5.2 偷看产生假设，不产生事实

验证方 Agent（或 sub-agent）**可以**去看另一侧的代码或测试。但它看到的只能成为**待对照契约检验的假设**——**绝不能**成为新的事实基准。看到实现返回 `"1"`，产生假设"也许字符串是有意的"；这并不授权它接受 `"1"`。该假设随后对照契约与意图来裁定。

### 5.3 出现失配时的三种结局

当实现与 spec（由测试编码）相左时，Agent 的**第一反应被禁止落在产物层**——不许动断言、不许动返回值去把红弄绿。回到契约，问"系统*本意*该做什么"，恰好得到三者之一：

- **A）实现违反了正确的 spec** → 修实现。
- **B）测试违反了正确的 spec** → 修测试。
- **C）实现揭示了 spec 错了或没说**（字符串 `"1"` 的精度情形）→ 这是一次 **spec reconcile，不是作弊**。有意识地修订 spec，在 `notes` 里记下*为什么*（若改动属于契约层、跨模块或不可逆，则按 §1.1 升级），然后把实现**和**测试**双向**对齐到修订后的契约。

### 5.4 试金石

为把合法的 reconcile（C）与"对着答案改问题"区分开，Agent 自问：

> *如果我把这个改动当作"系统应该怎样"的决定，大声讲给用户听，它站得住脚为一个真实的设计决定吗——还是听起来只是"我把红色弄没了"？*

若诚实的回答是后者，停下、升级。作弊与 reconcile 的区别在于**方向**（是关于意图行为的决定驱动契约，而非产物驱动契约）、**有意识**（刻意，而非阻力最小路径）、以及**有记录**（理由被写下并传播到双方）。

### 5.5 Sub-agent 交叉校验

用 sub-agent 互相交叉核对，而不是去筑一道硬墙。一种常见而有效的模式：一个 sub-agent 照 spec 实现，另一个照同一份 spec 写测试，各自独立锚定到契约；二者输出之间的失配，是应用 §5.3 的高信号提示。价值不在保密——在于**从同一契约出发的两次独立推导**，它会暴露契约歧义与单边假设，而这些是单个 Agent 会悄悄朝有利于自己的方向消化掉的。

## 6. 任务规模分级（要多少仪式）

文档量随任务缩放。挑错档位——给一行修复套整套 spec 仪式——是经典的 SDD 反模式。

| 档位          | 典型任务                            | 文档                                                                                       |
| ------------- | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| **Quick-fix** | 一行 bug、错别字、琐碎调整           | 不写新 spec。直接改；在 `changelog` 记一行（若做了真实决定，再在 `notes` 记一行）。读长存层以获取护栏。 |
| **Feature**   | 一个自成一体、有分量的功能或 bug     | 一个 episode：`spec`（本次变更的契约）+ 一份轻量 `plan` + `notes`。仅当变更触及架构或原则时才 reconcile 长存文档。 |
| **Module**    | 一个新模块或一次重大重构             | 完整 episode，外加更新/起草该模块的长存层（`requirements`、`design`，可能还有 `blueprint`）。跨模块影响须升级并冒泡。 |
| **Greenfield**| 一个从零开始的新项目或子系统         | 先（与用户一起）确立长存层：`philosophy`、`requirements`、`design`、`goal`、`blueprint`。然后逐模块按 **Module** 档推进。这是唯一真正"先文档"的档位。 |

拿不准时，降一档。一个事后发现比预期大的任务，补文档很便宜；而一个小任务本不需要的仪式，趟过去很贵。

> 深度上限，依然有效：在一个任务内，最多为**当前模块加它的直接子模块**写长存文档。再往深，就是在做用户尚未表达的设计决定。列出更深子模块的名称与职责，然后停下，提议把它们作为各自的任务处理。

## 7. 工作流回路

对一个 **Feature** 或 **Module** 档任务（Quick-fix 缩减，Greenfield 在前端扩大）：

1. **理解意图。** 读本文件、长存层（`philosophy`、`requirements`、`design`、`blueprint`、`goal`），以及活动的 `spec`/`plan`（若有）。除非有具体理由，**不要**载入归档的时间线 episode。
2. **起草契约。** 把 episode 的 `spec` 写（或更新）到 §4.1 的精度——边界锚定、内部放空。对 Module 档及以上的任何东西，与用户确认范围/DoD。
3. **构建并验证。** 照 spec 实现；照 spec 与意图验证（§5）。Sub-agent 可交叉校验。内部惊喜：拍板并推进。
4. **Reconcile。** 若一个发现属于契约层，先更新 spec（按 §1.1 在需要时升级），传播到实现与测试，并把原因记入 `notes`。若它触及架构或原则，reconcile 长存层。
5. **归档。** 完成时把 `spec`/`plan`/`notes` 移入 `timeline/<时间戳>.<kind>.<topic>/`，冻结。更新 `changelog`（带冒泡）。把任何跨 episode 决策记入 `decisions.md`。
6. **核对 code-as-docs。** 公开 API 带与 spec 一致的 doc-comment；关键段落带行内注释（§8）。

两个家族各按自己的节奏推进：**长存层**只在意图或架构确实变动时才触碰；**时间线**每个任务都前进。

## 8. Code as Docs

文档套件不取代代码内注释；两者互补。文档承载项目/模块级的"为什么、做什么"；注释承载函数/行级的"这段为什么这么写"。

- **公开 API** 带 doc-comment（Doxygen/JSDoc/docstring/Rustdoc 风格），内容与 spec 一致。
- **关键段落**带行内注释：非显然的算法选择、性能关键路径、边界处理、以及任何直接实现某条 spec 条款的代码。
- 注释要**重述**，而非仅仅**引用**。把推理写在行内（"token 必须是 HS256 JWT；过期 → `TokenExpiredError`"），而不是"见 `spec` §3"。代码应当无需切换到文档即可读懂。这种冗余是刻意的，服务于人类读者。
- 契约变更时，其代码注释随之变更。这是任何实现任务的收尾检查项。

---

## 9. 依赖管理

1. **用命令行工具管理依赖**（`npm`、`cargo`、`go`、`uv`……），不要手改配置文件；除非用户另有说明，默认用最新版本。
2. **优先选开源、广受尊重、活跃维护**的依赖；对约两年未更新的东西保持警惕。
3. **避免厂商锁定**（§1.2）；在 `design` 中记录接受/否决理由。
4. **最小化供应链攻击面**——在专注的小工具够用之处，宁选简单、自包含、依赖链浅的库，而非大型框架。
5. **没有合适的就自己造**，当没有现成依赖满足上述原则时。

---

## 10. 文档语言

- 文档套件**默认英文**。
- **中文翻译非强制**；仅在用户明确要求时产出。
- 若某模块已有中文镜像，任何文档变更都要**双侧同步**更新。
- 中英不一致时，以英文为事实来源——但 Agent **不**自行修改任一侧。升级（§1.1），问哪一侧反映正确意图，再据此修正（也可能是英文错了）。

## 11. 自检清单

**任务开始前：**

- [ ] 我读了本文件、长存层、以及活动的 `spec`/`plan` 吗？
- [ ] 我有没有正确地*避免*载入我并不需要的归档时间线 episode？
- [ ] 这个任务是哪一档（§6）？我即将施加的仪式量对不对——不是大锤砸核桃吧？
- [ ] 用户指令与长存文档一致吗？若不一致，我把冲突摆出来了吗（§1.1）？
- [ ] 我清楚哪些决策属于契约（锚定 + 可能升级）vs 构造（拍板并推进）吗？

**任务结束前：**

- [ ] 我是否在**契约**层而非靠悄悄把红弄绿来解决任何测试/实现失配（§5）？每个这类改动都能通过 §5.4 的试金石吗？
- [ ] 内部惊喜是否留在了内部，而契约变更是否被 reconcile + 记录（§4.2）？
- [ ] episode 是否已归档到 `timeline/`，且 `notes` 写明了为什么？
- [ ] `changelog` 是否已更新、并在有对外影响处冒泡？
- [ ] 我是否**仅在**获得用户批准时才触碰 `philosophy` 或任何长存原则文档？
- [ ] 公开 API 的 doc-comment 与关键段落注释是否就位、且与 spec 一致（§8）？
- [ ] 若存在中文镜像，它是否同步（§10）？
